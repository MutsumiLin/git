# 第一轮需求与验收

依据《2026版软件工程实验指导书》的本题要求，第一轮提交一个可工作的“登录、上报、发分、查询”增量，同时建立后续商城和运营功能的接口边界。老师已同意六人一组。

## 角色

| 角色 | 场景主体 | 本轮目标 |
| --- | --- | --- |
| 市民 USER | 市民用户 | 上报本人的模拟行程，查询自己的积分和流水，浏览商品 |
| 运营 ADMIN | 平台运营部门 | 登录工作台，查看全部商品和当前规则 |
| 商户 MERCHANT | 入驻商户 | 登录工作台，只查看本商户商品和当前规则 |

## 核心规则

比较基准私家车 0.200、公交 0.080、地铁 0.050、骑行 0.000，单位均为 kgCO2e/人公里。全部为教学模拟系数。

`减排量=max(0,里程×系数差)`；`积分=floor(减排量×100)`。中间计算不按页面显示精度提前取整，保存六位小数。

里程 0.01—100.00，最多两位小数。仅支持 BUS、METRO、BIKE。完成时间必须有效且不晚于服务器时间。零分行程仍保留流水。

clientTripId 为 8—64 位 ASCII 字母、数字、下划线或连字符，服务端统一小写。相同用户和编号的模式、规范化里程、UTC 微秒完成时间一致时返回原结果；内容不同返回 409。网络结果不确定时，前端保留同一请求到会话存储，使用原编号重试。

账户余额等于积分流水 delta 合计。每条行程只有一笔奖励流水；所有身份来自服务器登录会话，不能由请求 userId 指定。

## 主要用例

UC01 登录与退出；UC02 上报行程；UC03 查询本人行程；UC04 查询积分和流水；UC05 浏览商品；UC06 查看运营或商户工作台。

UC02 前置条件为已登录市民且有积分账户。主流程为校验输入、锁账户、查幂等、读取规则、计算并保存行程、发布事件、记积分与流水、提交。异常流为输入不合法、请求内容冲突、监听器异常；失败时所有业务写入回滚。

UC03 和 UC04 的查询范围由当前会话确定；查询他人行程详情返回 404，不泄露记录归属。UC05 的用户列表隐藏草稿和下架商品；商户视图只按会话 merchantId 查询。

## 名词短语与 CRC 初稿

提取用户、商户、行程、规则、减排量、账户、积分流水、商品、库存。筛选后，交通方式为枚举，减排量和库存为实体属性；规则版本、行程、账户、流水、商品为核心对象。

| 对象 | 职责 | 协作者 |
| --- | --- | --- |
| UserAccount | 身份、角色与商户绑定 | Merchant、PointAccount |
| CarbonRule | 提供不可变模拟系数 | CarbonCalculator、TripService |
| TripRecord | 保存原始行程与计算快照 | CarbonRule、PointLedger |
| PointAccount | 保存可用积分 | UserAccount、PointLedger |
| PointLedger | 保存每次奖励及变更后余额 | PointAccount、TripRecord |
| Product | 保存上架条件和库存 | Merchant、CatalogRepository |

## 非功能需求

后端执行角色检查和数据隔离；数据库使用唯一键、行锁和事务保护账本；密码 BCrypt 散列，Session Cookie 为 HttpOnly。日志不向客户端暴露 SQL 或密码。接口统一错误格式，列表限制分页大小。重启保留业务数据，按 README 可重新部署。

本轮未提出已验证的性能 SLA；并发测试针对账本正确性，不代表生产容量。第一轮每个 Sprint 的实际起止时间、人员人工验收及回顾应由组员据实补充。

## 后续 Backlog

第二轮：商品维护、规则发布、兑换事务、订单与库存、核销初版。第三轮：核销清算、统计和全流程联调。第四轮：完整测试、部署演练、报告和答辩。后续状态不能写成第一轮已完成功能。
